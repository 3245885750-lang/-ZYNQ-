# PS/PL 集成踩坑清单

条目格式：触发条件 → 经验来源 → 排查步骤 → 修复方向 → 验证闭环 → 失效条件。证据文件名对应 [来源与验证边界](sources_and_limits.md)；实例参数需要替换成新工程的实际值。

## K01：下载成功，复位却一直有效

**触发条件**：FPGA配置正常，DMA或PL寄存器访问超时，或数据计数一直不动。

**经验来源（真实故障）**：10月22日记录中，两个复位IP实际生成配置为 `C_AUX_RESET_HIGH=0`，同时 `aux_reset_in` 固定接0，导致低有效辅助复位一直触发。此前自写模块仿真未覆盖厂商复位IP。当前重建脚本显式设置为1，与常量0的非激活连接匹配。见 `reset_observation_20261022.md` 与 `source_excerpts.md`。

**排查步骤**：

1. 先区分AXI访问超时和访问成功但数据为0；核对目标地址确实属于当前bit的外设。
2. 检查AXI时钟是否存在、复位控制器的输入极性与常量、锁定信号和时钟域。
3. 查看实际生成BD/IP配置或网表，核对 `peripheral_aresetn` 的释放；不能只看原Tcl或信号名字。
4. 用复位输出/时钟证据区分“复位未释放”和“地址或互连错误”，不先修改分类算法。

**修复方向**：让复位输入的非激活电平与IP实际配置一致。来源工程选择显式配置高有效并接0；另一工程也可能正确使用低有效并接1。修改后重建配套硬件。

**验证闭环**：包含厂商复位行为的仿真覆盖上电释放和再次复位释放；之后实际确认寄存器可访问、DMA计数推进。历史记录保存了问题与修复方向，本次没有重跑该复位仿真或进行实板复测。

**失效条件**：时钟不存在、DDR未初始化、AXI地址错误和跨域故障也可能产生相似现象；未查明输入电平/极性前，不能直接把所有复位参数改成1。

## K02：计时器频率宏没有括号，计算单位悄悄变了

**触发条件**：微秒时间不连续、毫秒超时过快/过慢、起音观察时间异常，但CPU和网络均在运行。

**经验来源（代码缺陷与修复验证）**：实际BSP定义 `XSLEEPTIMER_FREQ = XPAR_CPU_CORE_CLOCK_FREQ_HZ/2`，`COUNTS_PER_SECOND`再引用它。表达式 `t / COUNTS_PER_SECOND`会展开为 `t / CPU_FREQ / 2`，与 `t / (CPU_FREQ/2)`不同；取模表达式也会受影响。已改为先用括号求频率并赋给64位局部变量。见 `source_excerpts.md`、`integration_scope.json`、`clock_pc_checks.json`。

**排查步骤**：

1. 顺着BSP头文件展开宏，或用编译器预处理输出核对最终表达式；不要把宏名当成单一常量。
2. 记录计数频率和返回单位；核对 `sys_now` 是否按当前lwIP接口返回毫秒。
3. 选择0、约100ms、1秒边界两侧、60秒与较长运行区间，比较参考时间；检查严格递增和边界跳变。
4. 同时检查计数器位宽、回绕及乘法溢出。修复优先级问题不自动解决其他计时问题。

**修复方向**：例如 `const uint64_t frequency = (COUNTS_PER_SECOND);`，再计算 `(t/frequency)*1000000U + (t%frequency)*1000000U/frequency`，确认频率非零并评估最大运行时间。局部变量也便于检查实际频率。

**验证闭环**：来源工程修复后6100个测试输入单调、60秒换算正确；本机UDP/HTTP三类数据链路通过。该结果不是远端实收或真实计时精度校准。

**失效条件**：计数源或CPU频率变化需重测；两个设备的时间戳不能直接相减推算延迟，除非已经建立共享时间基准。

## K03：bit、初始化、ELF和诊断地址来自不同版本

**触发条件**：换ELF后能启动却读出异常邮箱，换bit后寄存器布局不对，复制工程后依赖旧盘符，或交接包只有适配层而缺少真正主程序。

**经验来源（交接观察）**：早期交接材料需补齐真实底座与采音分类主程序；10月25日版本采用JTAG桥接，11月2日版本已集成GE_PS，不能把早期状态套在新版上。11月4日整理时通过来源哈希和源码比对确认当前版及IDE导入版一致，并验证XSA内bit/init与下载载荷配对。见 `collection_provenance.json`、`package_checks.json` 和 `rebuild_comparison.json`。

**排查步骤**：

1. 列出当前实际加载的bit、XSA或hwh、初始化、ELF、BSP、寄存器定义与身份/符号表来源，记录文件哈希。
2. XSA有内嵌bit/init时逐字节比较；只有hwh等元数据时检查其生成来源和地址映射，不能假定它等同XSA。
3. 用当前ELF的符号表重新导出诊断地址；旧版地址不可仅凭同名变量继续使用。
4. 解压到新目录做只读完整性检查，重编应用，确认没有原工作区依赖。相同工具链下比较加载段，说明是否排除了调试路径和build-id。

**修复方向**：按同一个发布标识收集配套材料；保留原发行载荷，重编输出单独保存。改源码后更新身份、符号和清单，并重新验证。

**验证闭环**：当前工程的配对、源码身份、ELF地址记录及严格重编比对均通过。这个结论确认材料一致，不能证明实际麦克风、电气连接或网络已正常工作。

**失效条件**：哈希清单自己过时或引用错误来源时，哈希一致仍可能整套错误。没有XSA内嵌bit时，应使用可追溯构建记录，不编造配对证明。

## K04：AXI背压下，TLAST或FIFO计数不成立

**触发条件**：连续数据偶发缺样、DMA帧末尾异常，消费端停顿后数据不连续，丢弃统计与实际数量对不上。

**经验来源（RTL兼容修复与仿真）**：来源版本将 `m_axis_tlast = rd && last_sample` 改为 `m_axis_tvalid && last_sample`，使末尾标记不因接收方撤销ready而消失；FIFO满且同周期读出时仍允许写入，并增加饱和丢弃计数。见 `pl_compatibility_changes.diff`、`audio_backpressure_verified.log`。

**排查步骤**：

1. 对每个时钟只在 `TVALID && TREADY` 时认定传输成功；帧内计数应依赖成功握手。
2. 当 `TVALID=1,TREADY=0` 时，检查TDATA及TLAST等有效载荷是否保持稳定，直到成功握手。
3. 分别覆盖空、满、满时同时读写、长时间背压和复位；不要只跑ready恒为1的理想流。
4. 用生成、接收、丢弃和缓冲占用建立守恒关系。测试结束并排空后可检查生成=接收+丢弃；未排空时要计入库存。

**修复方向**：帧末标记属于有效载荷；满时同时读写能否接纳新样本应与FIFO实现一致；不可阻塞的实时源需要可观察的溢出/丢弃策略。未使用支路也要检查其ready传播，不能让它无意阻塞共享上游。

**验证闭环**：历史仿真报告798次停顿，生成340、接收319、丢弃21，满足排空后的数量关系。本例明确包含有意制造的溢出，不能写成“零丢帧通过”。

**失效条件**：跨时钟FIFO、异步采样、DMA缓存与DDR一致性另需专项检查；不能把同步FIFO补丁原样套用到异步FIFO，也不能随意丢弃新项目所需的数据分支。

## K05：输出类别少了，协议槽位却没有变

**触发条件**：模型升级后PC标签错位、分数条对应错误、出现停用类别，或用历史九类指标声称当前七类实板准确率。

**经验来源（接口变化观察）**：来源模型保留九个输出槽位，通过掩码127启用前七槽，玻璃破碎/发动机置零后按策略归一化；这不是七类重新训练。当前源码使用闭集top-one策略，不能据此声称未知类别能被拒识。见 `source_excerpts.md`、`native_verification.json`。

**排查步骤**：

1. 分开核对模型原始输出维度、线上协议槽位数、启用掩码与PC显示字典。
2. 用实际类别ID逐槽检查两端映射；不能删除中间元素后依靠数组位置自动重排。
3. 核对权重身份与C导出参数；检查停用槽、归一化、非法值和状态字段语义。
4. 明确分数是否校准概率、是否存在拒识逻辑，区分训练/验证/实板数据及当前启用策略。

**修复方向**：为协议维度和类别映射保留明确版本；PC按ID解码并校验启用状态。训练维度、协议槽位、显示类别数分别记录。

**验证闭环**：历史验证有8组CNN内核、147组流式数值对照和7项不连续性检查；当前源码明确掩码和九槽策略。数值一致不等于识别准确率高，本次技能包未重跑整个模型实验。

**失效条件**：多标签、开放集或动态词表需采用自己的输出语义；不能强制使用九槽或掩码127，也不能把被屏蔽类别简单当成正确拒识。

## K06：一个流的新包，掩盖另一个流已经过期

**触发条件**：频谱一直刷新但类别是旧的；页面要等分类才更新角度；断流或重新上电后旧结果继续显示；重复包被当成新观测。

**经验来源（协议与验证观察）**：DOA、classification、spectrum共用启动会话，但各有独立序号与更新节奏；本机C编码到UDP/HTTP的三流链路通过，频谱重复包和过期检查通过。历史记录也要求按流清理实时标记。见 `clock_pc_checks.json`、`spectrum_checks.json`、`pc_interface_original.md`。

**排查步骤**：

1. 以 `(session,kind)` 跟踪序号和最近有效接收时刻；分别统计重复、乱序、缺口与超时。
2. 新会话到来时，按协议清理旧会话的其他流状态，不把旧分类与新角度拼成同次观测。
3. 各流收到有效数据后独立更新；收到频谱不能刷新分类的有效期。
4. 测试只断一个流、全部断开、重启、重复和乱序。序号是固定宽度时，按协议处理回绕；时间戳/序号字段不要在前端悄悄丢精度。

**修复方向**：页面绘制最新有效状态，独立执行过期处理；需要暂时保持上次结果时显式标注保持状态，不能继续标为实时新结果。

**验证闭环**：先用本机回环验证解码和状态更新，再在目标PC记录真实收包，分别验证每类流断开与重启。已有证据只支持相应回环与频谱状态检查，不宣称全套远端异常场景均已完成。

**失效条件**：无会话或无序号协议只能做能力范围内的判断；必须同步多传感器帧的应用还要设计对齐和缓冲，不能直接使用“各流最新值”替代同步需求。

## K07：100ms步长被当成100ms端到端响应

**触发条件**：缩短推理步长后页面刷新变快，就宣称识别延迟相同地降低；用软件时间戳减PC时间推算声学响应。

**经验来源（设计与交接观察）**：来源系统保持约2秒音频上下文、100ms目标分类步长；频谱每5个1024样本DMA帧更新，原始采样率48,828.125Hz，对应约104.8576ms。已有说明明确不以此承诺端到端小于300ms，实板负载与声学响应仍待测。见 `performance_original.md`、`verification_summary.json`。

**排查步骤**：

1. 分列音频/传感器窗口、目标步长、任务排队、最坏计算耗时、网络和页面绘制间隔。
2. 用真实采样频率算帧时长，保留分数频率，避免把48,828.125Hz误写为48kHz。
3. 区分初次填窗、稳态刷新、声音切换/事件起点到正确结果，以及界面延迟。
4. 记录漏窗、采样丢失、结果年龄和最坏处理时间；更频繁推理可能提高总体负载。

**修复方向**：性能表标明“配置/标称/离线测量/实板测量”；端到端响应使用同一外部时钟、同步采集或录像对齐发声和显示。报告样本数、分布、最坏值与测试条件。

**验证闭环**：现有代码和记录确认这些参数与待测边界；它们没有提供本整合版真实端到端测量。复用者应以自己工程的实际计时填补，而不是复制一个漂亮数字。

**失效条件**：窗口、重采样率、处理器或调度变化后需重新评估；不同设备的时钟未同步时，两个时间戳直接相减不能证明端到端时延。
