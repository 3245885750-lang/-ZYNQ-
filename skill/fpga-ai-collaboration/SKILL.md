# 大模型协作提示词工作流（FPGA 长工程）

## 适用场景

用一个 AI 助手（Claude / Copilot 等）持续参与一个跨月、跨工具链的 FPGA 项目：
RTL、仿真、Vivado、PS 固件、上位机、文档。项目足够长时，AI 最大的问题不是
「不会写代码」，而是**在错误的前提上高效地改错地方**。

不适用于：一次性脚本、独立算法题——那些直接问即可。

## 使用方法

### 1. 每次对话先给「不可协商的约束」

把以下内容固定成一段前置说明（本项目的 `CLAUDE.md` 就是这个角色）：

```
- 目标平台与器件（例如 XC7Z020，50 MHz，Vivado 2026.1）
- 谁负责哪一部分（我只负责 PL；PS 由队友负责）
- 硬约束（例：只能用某厂商芯片；不得损失精度与实时性）
- 禁止动作（例：不要启动综合/实现；只做只读检查）
- 交付节奏（例：上板一次很慢，改完先自查再给我）
```

### 2. 描述问题时，区分「现象」和「我的猜测」

坏例子：「显示角度跳变，帮我调一下限速。」
好例子：「在固定方位拍手，输出角度本身大幅跳变；不是轨迹不平滑。
数据在 `data/clap_log_20261101.csv`，逐帧值如下……」

**现象 + 原始数据 > 结论**。AI 会顺着你给的结论走；结论错了，它会很勤奋地
改错地方。

### 3. 要求「先取证、再改」

在提示词里明确写：

```
在改任何 RTL 之前：
1. 先指出你依据的是哪几行代码；
2. 给出你的判断依据（数据/波形/日志）；
3. 如果证据不足，先告诉我需要什么数据，不要猜。
```

### 4. 要求 A/B 与可回滚

```
改完不要直接给我结论。先说明：
- 旧行为 / 新行为分别是什么；
- 哪些场景会变、哪些不会；
- 用什么数据能验证（逐位回放/仿真/实测）；
- 如果效果不对，怎么一键退回。
```

### 5. 把结论沉淀到文件，而不是留在对话里

每次确认的事实写进 `CLAUDE.md` 或工程日志（本项目为
`report/ai_collaboration_log.md`、`report/doa_jump_investigation.md`），
并注明日期与依据。下一轮对话让 AI 先读这些文件。

### 6. 交接时给「文件路径 + 期望输出」，不给「请你理解整个项目」

AI 没有跨会话记忆。每次交接写清楚：

```
目标文件：src/pl/rtl/mvdr_axi_top.v
相关文档：report/doa_jump_investigation.md 第 8.7 节
期望输出：只改输出级，不给完整文件；给出 diff 与验证命令
```

## 已验证效果

本项目的 `report/ai_collaboration_log.md` 是这套流程的直接产物：19 条以上的
工程决策、踩坑与验证记录，均带日期和依据。实际收益：

- 修改 RTL 前先跑逐位回放，避免了一次上板周期（上板一次很慢）；
- 通过「先看代码再下结论」发现了一个 4 bit 计数器回绕缺陷；
- 文档中的参数与 RTL 用 `param_check.py` 自动比对，避免长期漂移。

## 失效条件

- AI 无法看到硬件波形和示波器；所有模拟量结论仍需人来确认。
- 长上下文会被截断，早先的约束可能丢失——因此约束必须落盘，不能只靠对话。
- 如果让 AI 直接跑综合/实现，可能与本机其他任务争抢资源导致卡死；
  工具链动作应由人控制。
